### USER
I wanna create a sea of stars HD2D like game but I needs tips on what size/res the overworld/world map should be, any recommendation?

### ASSISTANT
Rin, for a **Sea of Stars / HD-2D-style** overworld, I’d recommend not making one giant single image/map. Instead, build **tile-based region maps** and choose a virtual resolution that scales cleanly.

## My safe recommendation

### Best starter setup
- **Target display resolution:** 1920×1080  
- **Internal pixel resolution:** **640×360**  
- **Tile size:** **32×32 px**
- **Visible tiles:** about **20 × 11 tiles**
- **Character sprite:** roughly **24–40 px tall**
- **Overworld region size:** **80×80 to 128×128 tiles**

This scales perfectly to:
- 720p = 2×
- 1080p = 3×
- 1440p = 4×
- 4K = 6×

So it’s very safe for PC/console/Switch-style targets.

---

## If you want a more detailed “HD-2D” look

Use:

- **Internal resolution:** **960×540**
- **Tile size:** **48×48 px**
- **Visible tiles:** about **20 × 11 tiles**
- **Character sprite:** roughly **40–64 px tall**
- **Region size:** **96×96 to 144×144 tiles**

This gives you more room for detailed terrain, lighting, shadows, props, and HD effects, but it increases art workload and memory.

A nice thing is that:

- 640×360 with 32px tiles
- 960×540 with 48px tiles

give you roughly the same camera framing, just with more pixel density/detail in the second option.

# Overworld / world map size recommendations

## For traversable overworld regions

Do **not** make the entire world one huge map. Make separate regions/islands/areas and load them individually.

### Good sizes

| Region type | Recommended size | Pixel size at 32px tiles | Notes |
|---|---:|---:|---|
| Small area / route | 48×48 to 64×64 tiles | 1536–2048 px | Good for early-game areas |
| Standard overworld region | 80×80 to 128×128 tiles | 2560–4096 px | Best starting point |
| Large island / region | 144×144 to 192×192 tiles | 4608–6144 px | Use chunking/streaming |
| Massive open world | 256×256+ tiles | 8192+ px | Avoid unless you really need it |

For a Sea of Stars-like game, I’d start with something like:

> **96×96 tiles at 32px = 3072×3072 px**

or, for a more detailed version:

> **96×96 tiles at 48px = 4608×4608 px**

That’s large enough to feel like an explorable region, but not so large that it becomes empty and painful to fill.

# World map / world select screen

If by “world map” you mean the map where the player selects locations, flies around, or sees the world from above, then it’s different from a fully playable overworld.

## For a world select map

Recommended:

- **Design layout at:** 1920×1080
- **Pixel-art version:** 640×360 or 960×540
- **Background texture size:** 2048×2048 or 4096×4096 max
- **If zooming heavily:** use chunks/tiles instead of one giant image

For a simple world map screen:

> **2048×2048 px** is usually safe.  
> **4096×4096 px** is okay on desktop/console, but can be heavy on mobile.

If the player can pan and zoom a lot, don’t make one huge image. Use tiled/chunked maps or vector/UI-based map icons.

# Tile size advice

For a Sea of Stars-inspired top-down / 3/4 RPG style, common tile sizes are:

| Tile size | Feel | Best use |
|---:|---|---|
| 16×16 | Very retro, chunky | SNES-style, low detail |
| 32×32 | Balanced | Great default for RPG overworlds |
| 48×48 | More detailed, HD-2D friendly | Good for detailed terrain/lighting |
| 64×64 | Large, cinematic | Good for detailed scenes, but less visible area |

My recommendation:

> Use **32×32 tiles** if you want easier production and clean scaling.  
> Use **48×48 tiles** if you want more detailed HD-2D environments.

# How much should the camera see?

For top-down RPG exploration, a good visible range is usually:

- **15–25 tiles wide**
- **8–14 tiles tall**

For overworld travel, you may want more:

- **20–30 tiles wide**
- **12–16 tiles tall**

For towns/dungeons, you may want less:

- **15–20 tiles wide**
- **8–12 tiles tall**

Example:

If your internal resolution is **960×540** and your tiles are **48×48**:

- Horizontal visible tiles: `960 / 48 = 20`
- Vertical visible tiles: `540 / 48 ≈ 11.25`

So the player sees around **20 × 11 tiles**, which is a nice RPG framing.

---

# Best “HD-2D” workflow

For that HD-2D feel, the trick is usually:

1. Keep the world/tiles/sprites pixel-art based.
2. Use a low internal resolution for pixel art.
3. Add high-resolution effects on top.

For example:

- Pixel-art tiles/sprites at 640×360 or 960×540
- Upscale to 1080p/4K with nearest-neighbor / point filtering
- Add high-res:
  - lighting
  - bloom
  - depth of field
  - particles
  - water shaders
  - fog
  - color grading
  - shadows
  - parallax layers

This gives you the mix of retro pixel art and modern presentation.

# Engine-specific starting points

## If using Unity

For a 640×360 setup:

- Reference resolution: **640×360**
- Pixel Perfect Camera: enabled
- Upscale Render Texture: enabled
- Sprite Pixels Per Unit: **32** if using 32px tiles
- Grid Cell Size: **1 × 1**
- Camera orthographic size:  
  `360 / (2 * 32) = 5.625`

For a 960×540 setup with 48px tiles:

- Reference resolution: **960×540**
- Sprite Pixels Per Unit: **48**
- Camera orthographic size:  
  `540 / (2 * 48) = 5.625`

Interestingly, both have the same orthographic size if you use those tile/res combinations.

---

## If using Godot

Recommended project settings:

- Viewport width: **640**
- Viewport height: **360**
- Stretch mode: `viewport`
- Stretch aspect: `keep`
- Texture filter: **Nearest**
- Integer scaling: enabled if possible
- Tile size: **32×32** or **48×48**

For higher detail:

- Viewport: **960×540**
- Tile size: **48×48**

# Map chunking

If your map is larger than around **4096×4096 px**, I’d recommend chunking.

Good chunk sizes:

- **16×16 tiles**
- **32×32 tiles**
- **1024×1024 px**
- **2048×2048 px**

For example:

A 128×128 tile map with 48px tiles is:

> 6144×6144 px

That’s too large to treat as one simple texture in some cases, so break it into chunks.

---

# Scope advice

A common mistake is making the overworld way too big too early.

Instead of:

> “I’ll make a 500×500 tile world immediately.”

Do this:

> Make one polished 64×64 or 96×96 region first.

Fill it with:
- 2–3 biomes
- a town
- a dungeon entrance
- a few secrets
- clear landmarks
- readable paths

Then expand.

A good rule:

> Every 1–2 screens of movement should have something interesting: a landmark, encounter, treasure, path choice, or story beat.

> **Overworld region size:** 96×96 tiles  
> **Pixel size:** 3072×3072  
> **World map screen:** 1920×1080 layout, pixel background at 640×360 or 960×540

> **Internal resolution:** 960×540  
> **Tile size:** 48×48

# Tile size recommendation

At **640×360 internal resolution**, I recommend:

## Best default overworld tile size

> **32×32 px tiles**

At 720p, those tiles will appear as **64×64 px** on screen because of the 2× scale.

### Why 32×32 tiles?

At 640×360 with 32px tiles:

- Horizontal visible tiles: `640 / 32 = 20`
- Vertical visible tiles: `360 / 32 = 11.25`

So the camera sees roughly:

> **20 × 11 tiles**

That is a very nice RPG framing for overworld/town exploration.

---

## More detailed option

If you want larger, more detailed HD-2D-style tiles, you can use:

> **48×48 px tiles**

At 640×360, this gives:

- Horizontal visible tiles: `640 / 48 ≈ 13.3`
- Vertical visible tiles: `360 / 48 = 7.5`

So the camera sees roughly:

> **13 × 7.5 tiles**

This feels more cinematic and detailed, but much tighter. It can work for towns, dungeons, or battle maps, but for a large overworld it may feel zoomed in.

---

## Tile size summary for 640×360 internal

| Tile size | Visible tiles | Feel | Recommendation |
|---:|---:|---|---|
| 16×16 | 40 × 22.5 | Very zoomed out, retro | Too small for detailed HD-2D |
| 24×24 | 26.6 × 15 | Retro, wide | Okay, but less detailed |
| **32×32** | **20 × 11.25** | Balanced RPG view | **Best default** |
| 48×48 | 13.3 × 7.5 | Detailed, cinematic | Good for towns/battles |
| 64×64 | 10 × 5.6 | Very close | Usually too zoomed in for overworld |

My recommendation:

> Use **32×32 tiles** for overworld/towns.  
> Use **48×48 tiles** only if you want a more zoomed-in, detailed presentation.

# Character size relative to tiles

A useful rule:

> Character height should usually be around **1 to 1.5 tiles** for top-down RPG style.

Examples with 32×32 tiles:

| Character height | Relative size | Feel |
|---:|---:|---|
| 32 px | 1 tile tall | Small, classic |
| 48 px | 1.5 tiles tall | Nice RPG proportion |
| 64 px | 2 tiles tall | Large, heroic, more detailed |

For a Sea of Stars-inspired style, I’d aim for:

> **Character height around 1.25 to 1.75 tiles**

So with 32px tiles:

> **40–56 px tall characters** work well.

A practical sweet spot:

> **32×48 px** or **40×56 px**

# Props and environment objects

Use sizes based on your tile grid.

If your tile size is **32×32**, props should generally be multiples of 8, 16, or 32.

Good prop sizes:

| Prop type | Recommended size |
|---|---:|
| Small object | 8×8 or 16×16 |
| Medium object | 16×32 or 32×32 |
| Large object | 32×64 or 64×64 |
| Building / landmark | 64×64, 96×96, 128×128+ |

Examples:

- Rock: 16×16 or 32×32
- Tree: 32×64 or 64×96
- House: 96×96 or 128×128
- Bridge: 32×32 modular pieces
- Cliff/waterfall: 32×64 or 32×96 tiles

# Sprite sheet sizes

For characters, don’t make the sprite canvas exactly the character size. Add padding for animation, effects, weapons, hair, etc.

If your character is **32×48 px**, use frames like:

> **64×64 px per frame**

If your character is **48×64 px**, use frames like:

> **96×96 px per frame**

For a simple 4-direction walk cycle:

- 4 directions
- 4 frames each
- 16 frames total

A sheet could be:

> **256×256 px** or **512×256 px**

For more animation, attacks, idle, etc., use:

> **512×512 px** or **1024×1024 px** sprite sheets

For tilesets:

| Tile size | Good tileset texture size |
|---:|---:|
| 16×16 | 256×256 or 512×512 |
| 32×32 | 512×512 or 1024×1024 |
| 48×48 | 1024×1024 |
| 64×64 | 1024×1024 or 2048×2048 |

For most platforms, **2048×2048** is a safe maximum for sprite atlases unless you have a specific reason to go larger.

# If you want to render natively at 1280×720

You can also make your internal resolution **1280×720** instead of 640×360.

This gives you more detail, but your pixel art will be “smaller” unless you use larger assets.

To get the same camera framing as:

> 640×360 + 32px tiles

you would use:

> 1280×720 + **64px tiles**

## Native 720p equivalent setup

| Setting | 640×360 setup | Native 720p equivalent |
|---|---:|---:|
| Internal resolution | 640×360 | 1280×720 |
| Tile size | 32×32 | **64×64** |
| Character sprite | 32×48 | **64×96** |
| Large character | 48×64 | **96×128** |
| Small prop | 16×16 | **32×32** |
| Large prop | 64×64 | **128×128** |

This works if you want sharper UI, high-res effects, or more detailed 2D/3D backgrounds.

However, for pixel-perfect scaling, **640×360 is safer**, especially if you also target 1080p.

---

# Important: keep pixel scale consistent

Whatever you choose, keep your pixel scale consistent.

For example, if your tiles are 32×32 and your character is 32×48, then:

- 1 character pixel = 1 tile pixel
- 1 prop pixel = 1 tile pixel
- 1 effect pixel can be high-res if it’s an HD-2D effect, but the base art should match

Avoid mixing:

- 16px character
- 32px tiles
- 64px props

unless you intentionally want different scales. It can make the game look messy.

# HD-2D asset strategy for 720p

For an HD-2D look, you can do this:

1. **Pixel art layer**
   - Internal resolution: 640×360
   - Tiles: 32×32
   - Characters: 32×48 or 48×64
   - Props: 16–128 px

2. **HD effects layer**
   - Rendered at 720p or higher
   - Lighting
   - Bloom
   - Fog
   - Particles
   - Water shimmer
   - Depth of field
   - Color grading
   - Soft shadows

This gives you:

> Retro-style pixel art + modern lighting/effects

That is usually the core trick behind HD-2D-style visuals.

# UI resolution

Do not make your UI/text at low internal resolution if you want crisp text.

Recommended:

> Render UI at **1280×720 minimum**, or ideally at the final display resolution.

So:

- Game world: 640×360 scaled to 720p
- UI/HUD/text: 720p or native resolution

If you make UI at 640×360 and scale it, text may become blurry or chunky unless that’s the style you want.

## Runtime (the potato)

"Runs like Sea of Stars" effectively means **Switch-class / integrated-GPU-class**. Your budget:

- **Internal 640×360 = 0.23 MP** vs your screen's 4.1 MP → ~18× fillrate headroom. That's the whole reason the potato can afford your HD-2D lighting.
- Run **all post-FX (bloom, grade, light compositing) at internal res**, never at output res. Upscale once, at the end, point-filtered.
- **No MSAA** (pointless on pixel art), **no mipmaps on atlases** (saves ~33% VRAM), atlases capped at **2048×2048**.
- **Chunk the tilemap** (32×32 tiles per chunk). On-screen cost ≈ 9–16 chunks × 2–3 layers ≈ 30–50 draw calls. Trivial anywhere.
- Dynamic 2D lights: keep count low, composite light buffer at **half internal res** (320×180) and upscale. Big win, invisible loss.
- Add a **"Potato Sim" toggle in the editor**: forces the 640×360 RT, disables editor-only overlays/effects, shows draw calls / fillrate / chunk count. Your 4060 will lie to you otherwise.

## Realtime painting architecture (so the 4060 stays bored)

- Paint edits **tile data**, then mark the touched chunk dirty and rebuild **only that chunk's** vertex buffer/mesh. Never rebuild the world.
- Keep collision/autotile rules as data passes on the dirty chunk, not per-pixel GPU work.
- Editor-only visuals (grid, collision overlay, gizmos, selection) render as a **native-res overlay pass**, so they stay razor sharp at 16× zoom and cost the potato nothing (they're stripped in builds).
- Stream chunks in/out by camera distance in both editor and runtime — same code path, so playtesting in the editor is honest.

## Making the sculpt viz look pro (all math, zero painting)

Data textures (tiny): height `R16` 256×128 (64 KB), biome `R8`, props/objects `RG8` (id + variant), done.

Editor shader, one pass over the visible rect:

```hlsl
h     = Height.Sample(bilinear, uv);          // smooth is FINE here, it's viz
n     = normalize(float3(-dHdx, -dHdy, slopeStrength));
shade = dot(n, LightDir) * 0.5 + 0.5;         // hillshade <- the single biggest win
depth = SeaLevel - h;

col   = water ? DepthRamp(depth)              // 3-4 stop deep->shallow ramp
              : BiomeLUT(biome, heightBand(h)); // small LUT tex: biome x height band
col  *= lerp(1.0, shade, landMask);           // shade the LAND, not just water
col   = lerp(col, RockCol, slopeMask);        // cliffs read as cliffs
col   = lerp(col, SandCol, coastBand);        // shallow band, not an outline pen
col  -= ao * coastAO;                          // darken land near waterline
col   = lerp(col, ContourCol, contourMask);   // toggleable contour lines
// editor-only: animated foam/specular sparkle on water
```

Why this instantly kills the MS Paint feel:

- **Hillshade** gives land form. Flat green blobs become terrain. Bonus: wire it to your existing **Time: 08:00** control — rotate the light direction and tint with time of day. Your sculpt view gets a golden-hour mode for free.
- **Depth ramp + shallow band** replaces the blur with intentional water language.
- **BiomeLUT** means one consistent palette everywhere; no more default-green vibes.
- **Slope rock + coast AO** adds the edge hierarchy your coast stroke was failing to provide.

Then props: replace per-tile random tree pixels with **clustered instancing** — density mask → Poisson/Worley points → instanced editor-res icons with 2–3 size variants and rotation. Clusters read as forest; uniform dither reads as noise. In the bake step, the same points stamp your 32px prop sprites with a seed, so gameplay matches what you sculpted.

Toggles to keep it a *tool*: contours, grid at integer zooms, biome IDs, height bands, props on/off, hillshade strength.

## What's actually true here

- Qt's QRhi backends (D3D11, D3D12, Vulkan, GL) are statically linked **into Qt6Gui.dll**. So the prebuilt Windows Qt6Gui.dll has `d3d11.dll` (and `dxgi.dll`, `opengl32.dll`) in its **import table**, no matter which backend you select at runtime.
- Import table entries load the DLL at process start. So even a pure-Vulkan Qt app "loads" d3d11.dll — but makes **zero DX11 calls**.
- `d3d11.dll` is a **core Windows system DLL** present on every Win10/11 machine. Loading it creates no deployment risk and negligible cost. ## Why your in-game weather reads as "2 frames"

Grep the runtime weather code for these, in order of likelihood:

1. **Flipbook or frame index math:** `% 2`, `%2`, `int(t * fps) % N`, `frameIndex`, a 2-frame sprite sheet in the sprite editor.
2. **Quantized time:** weather time uniform updated from a coarse timer (2 Hz QTimer etc.) instead of per rendered frame → everything snaps between two states.
3. **Hash seeded by frame parity:** `seed = frame % 2` or `int(uTime) % 2`.
4. **Nearest-sampled scrolling texture at sub-texel speed:** at 640×360 with NEAREST filtering, a scroll of 0.3 px/frame renders as *hold-hold-hold-jump* — reads exactly like a few-frame loop even though the math is continuous.
5. **Integer-texel scroll offset:** `int off = int(t * speed) % size;` with speed < 1 texel/frame → same stepping.

The permanent fix isn't patching those — it's making loops **structurally impossible**: per-cell random phase + per-cell speed quantized to integer cycles per wrap period + world-space continuous math. Then even a 12 Hz update or a NEAREST sampler can't produce a visible repeat, because no two cells ever agree on phase.

```glsl
// hash/noise/fbm — paste once into a shared .glslh
float hash21(vec2 p){ vec3 p3 = fract(vec3(p.xyx)*0.1031);
    p3 += dot(p3, p3.yzx+33.33); return fract((p3.x+p3.y)*p3.z); }
float vnoise(vec2 p){ vec2 i=floor(p), f=fract(p); f=f*f*(3.0-2.0*f);
    float a=hash21(i), b=hash21(i+vec2(1,0)), c=hash21(i+vec2(0,1)), d=hash21(i+vec2(1,1));
    return mix(mix(a,b,f.x), mix(c,d,f.x), f.y); }
float fbm(vec2 p){ float s=0.0, a=0.5;
    for(int i=0;i<4;i++){ s+=a*vnoise(p); p=p*2.03+17.1; a*=0.5; } return s; }
```

## Runtime (potato) weather — loop-proof by construction

```glsl
// worldUV in TILE units. scale = cells per tile: runtime ~8 and ~14.
// streak width/length tuned so features stay >= 1 art px at 640x360.
float rainCells(vec2 worldUV, float scale, float slant, float t, float seed){
    vec2 q  = vec2(worldUV.x + worldUV.y*slant, worldUV.y) * scale;
    vec2 id = floor(q); vec2 f = fract(q);
    float r1 = hash21(id+seed);
    float r2 = hash21(id+seed+19.7);
    float r3 = hash21(id+seed+41.3);
    float cycles = floor(6.0 + 5.0*r1);          // INTEGER cycles per wrap => seamless wrap
    float y = fract(r2 + t*cycles/uWrapSec);     // per-cell phase: no global loop exists
    float x = 0.25 + 0.5*r3;
    float w = 0.20 + 0.10*r2;                    // >= ~1 art px at runtime scale
    float l = 0.35 + 0.30*r3;
    return smoothstep(w, w*0.35, abs(f.x-x))
         * smoothstep(l, l*0.40, abs(f.y-y));
}

float ripples(vec2 worldUV, float scale, float t, float seed){   // water only
    vec2 q = worldUV*scale; vec2 id = floor(q); vec2 f = fract(q)-0.5;
    float r1 = hash21(id+seed), r2 = hash21(id+seed+7.1);
    float cycles = floor(2.0 + 3.0*r1);
    float ph = fract(r2 + t*cycles/uWrapSec);
    float ring = smoothstep(0.07, 0.0, abs(length(f) - ph*0.45)) * (1.0-ph);
    return ring * step(r1, 0.55);
}

// usage in your runtime frag, after land/water color:
float gust  = 0.7 + 0.6*vnoise(vec2(uTimeSec*0.15, 4.2));        // slow wind swell
float slant = 0.30*uWindDir.x * gust;
float cov   = uRainIntensity;                                     // or texture(uCoverage, uv).r
float mask  = smoothstep(0.45, 0.65, cov);                        // spatial rain mask
float rain  = mask * (0.65*rainCells(worldUV, 8.0,  slant, uTimeSec, 11.3)
                    + 0.35*rainCells(worldUV, 14.0, slant*1.3, uTimeSec, 71.9));
col = mix(col, col*0.82, mask);                                   // wet ground, mask-only
col = mix(col, col + 0.10, waterMask * ripples(worldUV, 6.0, uTimeSec, 5.5) * mask);
col = mix(col, vec3(0.85,0.92,1.0), rain*0.15);                   // streaks, alpha <= 0.15
```

Why this can never look like 2 frames: every cell has its own phase (`r2`) and its own integer cycle count (`6..10`), so the composite state space is astronomical; the only wrap is `uTimeSec` at 1024 s, and integer cycles make even that seamless. Gust adds a non-periodic swell on top.

## Latitude wind-band curve — concrete values

```glsl
// phi = |latitude| degrees; returns zonal u (east+) and meridional v (north+)
// for the NORTHERN pattern; world v = sign(lat) * vAbs (mirror for SH).
float uZonal(float phi){
    return -5.0*exp(-pow((phi-10.0)/8.0, 2.0))    // easterly trades
           +7.0*exp(-pow((phi-45.0)/12.0,2.0))    // westerlies (jet-ish peak)
           -4.0*exp(-pow((phi-78.0)/10.0,2.0));   // polar easterlies
}
float vAbs(float phi){   // Hadley equatorward / Ferrel poleward / polar equatorward
    return -1.2 + 2.0*smoothstep(25.0,35.0,phi) - 1.8*smoothstep(55.0,65.0,phi);
}
// usage: wind0 = vec2(uZonal(phi), sign(lat)*vAbs(phi));
// + pressure-gradient term rotated by -25deg*sign(lat) (Coriolis flavor),
// + curl-noise gusts. The vAbs zero-crossing near ~28deg gives horse latitudes;
// coverage convergence (-divergence) makes the ITCZ cloud band emerge for free.
```

## Globe map-screen shader (ray-sphere, potato-safe, map screen only)

```glsl
#version 450
// reuses hash/vnoise/fbm from shared header
layout(location=0) in vec2 vUvNdc; layout(location=0) out vec4 o;
layout(binding=0) uniform sampler2D uHeightBiome;  // RG: height, biomeIdx (REPEAT,CLAMP)
layout(binding=1) uniform sampler2D uCovNight;     // RG: coverage, nightlights
layout(binding=2) uniform UBO { vec3 sunDir; vec2 windDir; float timeSec;
    float seaLevel; float yaw; vec3 atmoColor; } u;

vec3 rd(vec2 ndc, float yaw){
    vec3 d = normalize(vec3(ndc.x, ndc.y, -2.6));          // ortho-ish cam
    float c = cos(yaw), s = sin(yaw);
    return normalize(vec3(c*d.x + s*d.z, d.y, -s*d.x + c*d.z));
}
void main(){
    vec3 ro = vec3(0.0,0.0,3.2); vec3 d = rd(vUvNdc*2.0-1.0, u.yaw);
    float b = dot(ro,d); float disc = b*b - (dot(ro,ro)-1.0);
    if (disc < 0.0){ o = vec4(mix(vec3(0.02,0.02,0.05), vec3(0.05,0.06,0.12),
        vUvNdc.y), 1.0); return; }                          // space backdrop
    vec3 p = ro + d*(-b - sqrt(disc));
    vec2 uv = vec2(atan(p.z,p.x)/(6.2831853)+0.5, asin(clamp(p.y,-1.0,1.0))/3.14159265+0.5);
    vec2 hb = texture(uHeightBiome, uv).rg;
    float h = hb.x; float water = step(h, u.seaLevel);
    float ndl = dot(p, u.sunDir);
    float term = smoothstep(-0.10, 0.15, ndl);             // soft terminator
    vec3 alb = biomeColor(hb.y);                            // your LUT lookup
    alb = mix(alb, vec3(0.06,0.16,0.28), water);
    vec3 col = alb * (0.12 + 0.95*max(ndl,0.0));
    col += water * pow(max(dot(reflect(-u.sunDir,p), -d),0.0), 24.0) * term; // sea glint
    float cov = texture(uCovNight, uv).r;
    float cl = smoothstep(0.55,0.75, fbm(uv*vec2(6.0,4.0) + u.windDir*u.timeSec*0.002)
                          * (0.5+cov));
    col = mix(col, vec3(1.0)*(0.15+0.85*max(dot(p,u.sunDir),0.0)), cl*0.85);
    col = mix(col, col + texture(uCovNight,uv).g * vec3(1.0,0.8,0.5),
              (1.0-term)*step(0.5,h));                     // city lights at night
    col += pow(1.0 - max(dot(p,-d),0.0), 3.0) * u.atmoColor * (0.25+0.75*term); // rim
    o = vec4(col, 1.0);
}
```

## Stage 1 — Arm set per river cell (deterministic, wrapped X)

```text
bits: N=1, E=2, S=4, W=8
components of diagonal d: a = vertical (N|S), b = horizontal (E|W)
parity p = (x + y) & 1

entryArm(c):  din = direction of dominant inflow (0 if source)
              orthogonal din -> bit(din)
              diagonal din   -> p0: bit(opp(a))   p1: bit(opp(b))
exitArm(c):   dout = flowDir[c] (0 if sink at sea/lake)
              orthogonal dout -> bit(dout)
              diagonal dout   -> p0: bit(b)       p1: bit(a)
   // NE example: p0 = entry S + exit E ; p1 = entry W + exit N  (staircase)

arms = entryArm | exitArm
for each extra inflow neighbor n (confluence): arms |= bit(dir(n->c))
mask4 = arms   // after OR-fix: also set bit if neighbor's arm points at me
               // (guarantees zero visual gaps at parity transitions)
```

Sources end with a single arm (exit only), mouths with a single arm (entry only) — those two cases are exactly what the cap overrides catch.

## 1. Water is a volume: three planes + a depth field

You already have `waterLevel` (hydrology) and bed height. Derive **depth = waterLevel − bed** as an R8 field, quantized to gameplay steps:

| depth step | meaning | movement state |
|---:|---|---|
| 0 | dry | walk |
| 1 | wade | wade (0.6× speed, splash steps, wade sprite row) |
| 2 | swim | swim surface (swim sprite, ripple wake) |
| ≥3 | deep | swim + **dive allowed** (underwater plane) |

Render planes, back to front: **seabed layer** (its own biome tileset: sand/coral/rock/kelp) → **volume FX** (depth tint gradient, caustics masked to shallow, light shafts) → **surface layer** (your water autotiles + foam rim + ripple/wake decals) → **above-surface** (spray, waterfall sheets, mist). Shallow shows seabed at ~70% through tint; deep goes opaque. That single depth-driven blend is 80% of your ref's look.

## 2. Cliffs = quantized z-steps + face drawables

Quantize height into gameplay steps (e.g., 8 steps, face = 8px per step at 32px tiles). When neighbor Δstep ≥ 1, emit a **cliff-face drawable** whose base row = top row + 1 (face hangs *below* the ledge line — exactly your ref 3). Traversal: walkable Δ0; stairs/ramp tiles or climbable-vine props for up; jump-down allowed Δ ≤ 2 with fall anim. Land ground draws shifted up by `steps × stepPx`.

## 3. One sort key fixes all occlusion: `(baseRow, zLayer)`

| zLayer | content |
|---:|---|
| 0 / 1 | seabed ground / seabed props |
| 2 / 2.5 | underwater entities + bubbles / caustic decals |
| 2.8 | cliff faces (base row = top+1) |
| 3 / 3.5 | water surface + foam rim / ripple & wake decals |
| 4 / 4.5 | swimmers, boats / waterfall sheets + mist |
| 6 | land ground (z-shifted by steps) |
| 7 | land props + land entities, y-sorted together |
| 9 / 10 | cloud shadows, clouds, spray / UI |

This ordering makes all three hard cases correct automatically: water in front covers cliff-face bases; cliffs occlude seabed/lake behind them; entities on ledges never get their feet eaten. Golden-test these three cases as an occlusion matrix.

## 4. Movement state machine + battle contexts

`walk → wade → swim → (dive ⇄ surface)`, plus `boat` (board at dock/ship tiles; boat blocked from depth < 2; wake trail). Transitions get 4–8 frame anims (dive splash, surface pop, bubble trail underwater).

Encounters auto-derive a **BattleContext** from tile data at spawn point: `LAND / SHALLOW / SWIM / BOAT / UNDERWATER` (+ per-encounter override in the DB). Context selects: layer-stack subset for the battle backdrop, sprite variant rows, bob/float motion, and rule mods (fire weakened underwater, lightning boosted, wade movement cost, escape rules). ### P5 — Cliff-Face & Ledge Autotile (The 3/4 Depth Solver)
In 3/4 pixel art, a cliff face is drawn *on the high tile's grid space but visually drops down* to obscure the tile below it. The agent must bake this deterministically based on the Z-steps from P4.

```markdown
# P5 — Cliff-Face Autotile & Ledge Masking
## Concept
A cliff face is a drawable emitted on the HIGH tile, dropping down into the
LOW tile's screen-space. It must hook into the P4 sort key `(baseRow, zLayer)`
so cliffs properly occlude things behind them but get covered by water/fog.

## The 3-Bit Edge Mask (per cardinal drop direction)
For a tile at (x,y) with a drop to the South (tile x, y+1 is lower):
Check the 3 tiles along the drop edge: SW(x-1, y+1), S(x, y+1), SE(x+1, y+1).
- Bit 0 (Left):  SW is lower (1) or same/higher (0)
- Bit 1 (Center): S is lower (1) or same/higher (0) -> MUST be 1 to emit face
- Bit 2 (Right):  SE is lower (1) or same/higher (0)
Mask = (Left<<2) | (Center<<1) | Right. (Apply rotated logic for N/E/W drops).

## 8-Piece Table (Center=1 is mandatory)
| Mask (Bin) | Decimal | Piece Type | Visual Description |
|---|---|---|---|
| 010 | 2 | Straight Face | Clean vertical drop |
| 011 | 3 | Right Outer Corner | Cliff ends on the right |
| 110 | 6 | Left Outer Corner | Cliff ends on the left |
| 111 | 7 | Inner Corner | Cliff wraps around a pillar/peninsula |
| 001 | 1 | Right Pillar/Arch | Left is high, center low, right high (cave) |
| 100 | 4 | Left Pillar/Arch | Right is high, center low, left high |
*Note: 000 and 101/010 without center drop are invalid.*

## Variants & Overhangs
- Straight/Inner pieces get variant rolls (moss, ivy, crack) via hash(x,y).
- Overhangs: If tile (x, y-1) [above the high tile] is empty/cave, emit an
  "Overhang Lip" piece on top of the cliff face.
- Waterfalls: If hydrology `waterfall` flag is present on this edge, OVERRIDE
  the straight/inner mask with the Waterfall Sheet + Mist emitter.

## Bake Rules
- Runs on CPU worker when height edits. < 5ms per chunk.
- Emits drawables into the `zLayer = 2.8` (between seabed and water surface).
- Deterministic: same height map = byte-identical cliff mesh/quad list.
```

- **Interaction:** Drag-and-drop reordering via `QMimeData` or simple Up/Down arrow buttons on the widget header. Collapsible bodies to keep the timeline clean.
- **Live Preview:** A split pane at the bottom showing how the text parses with BBCode.

- Singleton or Context-owned object.
- `void startTimeline(const QString& id)` -> Parses JSON into an in-memory linked structure.
- `void advance()` -> Evaluates current node.

  - If `Choice`: emits `showChoices`, waits for UI `choiceSelected(int)` signal.
  - If `Signal`: emits custom Qt signal, auto-advances.
- **Game Integration:** The game loop checks `if (NarrativeDirector::isActive()) pause_gameplay();`.
- **Variables:** `NarrativeBlackboard` class holding `QVariantMap` for flags, ints, strings. Exposed to Lua/Blueprints if needed later, but native C++ for V1.

## Acceptance

### P8 — Smart Infrastructure: Roads, Bridges, and Routing
Roads in this engine are not just painted textures; they are a **Graph Network** that queries the Hydrology and Z-depth systems to auto-place bridges, stairs, and fords.

```markdown
# P8 — Road Network & Smart Infrastructure
## P8.0 Data Model
- `RoadGraph`: Nodes (Waypoints) and Edges (Segments).
- Edge Properties: `type` (Dirt, Cobblestone, Wood, Sand), `width` (1-tile, 2-tile), `tier` (Village, Highway).
- Pathfinding: CPU A* on the tile grid. Cost function penalizes: steep Z-drops, deep water, dense forests, and high slopes.

## P8.1 Road Autotile (The Overlay)
Roads render as an overlay pass (or baked into the chunk albedo) ABOVE the ground but BELOW entities.
- 4-bit cardinal mask (N=1, E=2, S=4, W=8). 16 pieces per road type.
- Includes straight, T-junctions, crossroads, and 45-degree corner caps.
- Variant selection (e.g., cracked cobblestone vs smooth) via `hash(x,y, seed)` to break up repetition.

## P8.2 Smart Intersections (The "Magic")
When a Road Edge crosses a tile, the baker queries the Hydrology and Z-depth layers to auto-emit infrastructure props:

| Condition at Road Tile | Auto-Emitted Prop / Drawable | Z-Layer |
|---|---|---|
| **Crosses River (Tier: Creek)** | Stepping Stones (Ford) | 3.5 (Above water) |
| **Crosses River (Tier: River/Major)** | Wood/Stone Bridge (length = river width at this cross-section) | 4.5 (Above entities) |
| **Crosses Lake Edge** | Pier / Dock connector | 3.5 |
| **Z-step Drop (Δ = 1 or 2)** | Stairs or Ramp (aligned to drop direction) | Matches cliff face |
| **Z-step Drop (Δ > 2)** | Block path (A* should have routed around, but if forced, emit "Rope Bridge" or "Ladder") | 4.5 |
| **Crosses Dense Forest** | Auto-clear trees in a 1-tile radius around the road (Tunnel effect) | - |

## P8.3 Bridge Generation Logic
1. Detect intersection between Road polyline and River banks.
2. Calculate the perpendicular width of the river at the crossing point.
3. Emit a Bridge Prop:
   - `width <= 2 tiles`: Single span bridge.
   - `width > 2 tiles`: Multi-span bridge. Auto-emit "Stone Pylon" props in the water at 3-tile intervals.
4. Bridge shadow: Emit a dark, semi-transparent decal on the water surface (`zLayer 3`) directly under the bridge (`zLayer 4.5`).

## P8.4 Gameplay Integration
- `MovementSpeed`: 1.5x multiplier on Road tiles.
- `EncounterTable`: Roads override the biome encounter table. (e.g., "Safe" on highways, "Bandits" on dirt roads).
- `Mounts/Carriages`: Only allowed on `width >= 2` and `type != Sand` roads.

## Acceptance
- Draw a road from Town A to Town B.
- It crosses a river -> Bridge auto-spawns, pylons in water, shadow on water.
- It hits a cliff -> Stairs auto-spawn.
- It hits a shallow creek -> Stepping stones auto-spawn.
- Golden test: Road network hash matches between Editor and Runtime bake.
```

### How to manage this as a Solo/Small Team Dev

You have just designed a **Magnum Opus**. To actually finish this without burning out, you must sequence the development strictly:

1. **Phase A: The Core Reality (P1 - P9).** Build the WorldSim, the Hydrology, the Z-Depth, and the Narrative Engine. **Do not build any combat yet.** Just walk around the beautiful, living, procedurally generated world in a "Debug Mode" where you can spawn enemies and watch them fight each other using basic stats.
2. **Phase B: Game 1 (The Chrono Lens).** Build the ATB combat, the Time Portals (P10), and the Narrative UI. Ship Game 1. This proves your engine works and gives you a finished product.
3. **Phase C: Game 2 (The Mana Lens).** Strip out the ATB combat. Bolt on the Physics/ACTION lens (P12). Reuse the exact same world, but tell a parallel story in a different Epoch.

**The Magic Trick:** Because all three games share the **Core Reality (P1-P9)**, a player's save file from Game 1 can be imported into Game 2 and Game 3. The "Legacy Events" (P10.3) will carry over. The forest they saved in Game 1 will provide the tactical cover bonus for their army in Game 3.
